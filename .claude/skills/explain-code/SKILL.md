# 讲解代码（只读）

目标：读者不打开源码也能理解“它负责什么、怎么执行、为什么这样设计”，并能顺着给出的位置回到源码核对。

不适用：要求修改、修复、重构、优化代码，或需要实测性能（用 `a8w4-perf-experiment` / `gpu-timing-protocol`）。讲解中可以静态估算性能，但不跑 benchmark。

## 硬性规则

1. **不修改代码**：不编辑、格式化、重命名、新建或删除任何源码、测试、配置文件。只运行只读命令（搜索、`git log/show/blame`、`python -c` 打印模块路径或签名、仓库自带的只读查询脚本）；除非用户明确要求，不安装依赖，不启动 GPU 任务、benchmark、调优或任何会写仓库/缓存的脚本。唯一例外：文档模式下只在 `<名称>.explain/` 目录内写讲解文件。
2. **先读再讲**：每个结论都要落到读过的代码上。不凭文件名、函数名、注释或 docstring 推断行为；注释与代码不一致时以代码为准，并指出不一致。
3. **区分事实与推测**：能被源码、文档、日志证实的直接陈述并给出处；不能证实的写成“推测：……（依据：……）”。不编造性能数字、论文和链接；引用性能数据要注明来自哪份文档或日志。
4. **给出位置**：提到的函数、类、关键代码段都附链接，如 `[func_name](path/to/file.py#L120-L168)`。对话中用工作区相对路径；文档模式中用相对 README.md 的路径（如 `../file.py#L120`）。行号必须来自实际读到的内容。
5. **中文讲解**：标识符、API、指令名保持原文；不常见术语首次出现时附一句中文解释。
6. 发现的 bug、隐患、可改进点只在“总结回顾”中指出（位置 + 理由），不动手修复。

## 流程

### 1. 确定目标和粒度

| 用户说法 | 目标 | 粒度 |
|---|---|---|
| 解释这段代码 | 编辑器选区；无选区时用当前打开的文件；仍不明确就问一句 | 片段 |
| 这个函数/类做什么 | 跳到对应定义 | 函数/类 |
| 讲解 xxx.py | 按文件名搜索；多处同名时优先当前工程、当前打开文件附近的，仍有歧义就问 | 文件 |
| 分析这个模块 | 指定的包/目录，或当前文件所在的包 | 模块 |

用户直接贴在聊天里的代码：先用其中有辨识度的一行在工作区搜索定位；找不到就按原样讲解，并说明缺少上下文。

### 2. 阅读目标源码

- 片段：连同所在的函数/类、用到的模块级常量和配置一起读，不只读选区。
- 文件：从 import 读到文件末尾；大段读取，少做零碎读取。
- 模块：先列目录，读 `__init__.py`、入口文件和 README，整理“文件 → 职责”表，再挑核心文件按文件粒度精读，不逐个文件平铺。
- 边读边记：对外 API（被其他文件 import 的名字）、主执行路径、编译期与运行期参数、分支和特殊情况、全局状态与副作用（缓存、注册表、环境变量）。

### 3. 追踪直接依赖和调用方（按需，以一跳为主）

- **依赖**：目标直接调用的项目内函数/类，跳到定义处弄清入参、返回值和副作用。标准库和常见第三方库只说明用途；只有理解目标必须知道其内部行为时（如 FlyDSL / Triton 原语的语义）才读已安装包的源码（`python -c "import flydsl, os; print(os.path.dirname(flydsl.__file__))"` 定位）。不为讲解无限递归。
- **调用方**：搜索对外符号名和模块导入路径（`from a.b import name`、`import a.b`、`a.b.name`），分成上层组件、测试、benchmark/脚本，每类挑 1-2 个代表，摘录实际传参作为用法示例。注册表、字符串分发、`getattr`、调优表选择等间接调用要搜注册名或字符串。调用方很多时给数量 + 代表样例。
- 范围大时可交给只读子代理（如 Explore）并行收集，但写进讲解的结论要回到源码核对。

### 4. 收集文档和历史

- 目标所在目录及上级目录中提到它的 README、设计文档、实验日志，以及注释里引用的论文/issue：提取设计过程、参考文献、实测性能。
- pyhip a8w4：在 `src/contrib/flydsl` 下运行 `python a8w4/exp.py grep <关键字>` 查实验索引，只读相关的 `experiments/log_*.md` 小节；verdict 为 `invalidated` 的数字不引用。
- 设计动机不明时查历史：`git log --oneline --follow -- <file>`、`git log -S '<symbol>' --oneline`、`git show <commit>`。
- FlyDSL kernel 的平台背景（JIT cache key、LDS 上限、VGPR 与 occupancy、跨 XCD 一致性等）参考 `flydsl-gfx942-pitfalls` skill。

### 5. 组织输出

按下节结构自顶向下、逐步细化。篇幅与粒度匹配：片段讲清 1-3 个要点即可，文件/模块才展开全部章节；不适用的章节直接省略，不留空标题。大文件在对话中只精讲主路径上最关键的几段，并提示可以“生成讲解文档”获得逐段讲解。

## 讲解结构

### 1. 概述
一两句话说明它是什么、解决什么问题、在系统中的位置（谁调用它、它调用谁），附位置。模块级加“文件 → 职责”表和模块关系图。

### 2. 职责与对外接口
- 主要功能。
- 对外 API 用表格逐个列出：名称（带位置）、参数（含义、shape/dtype/取值范围、默认值）、返回值、副作用与前置条件。
- 配一段调用方的真实用法（注明出处），说明典型参数从哪里来。

### 3. 执行流程与实现原理
本节不贴源码，用论文式的“文字描述 + 伪代码 + 示意图”讲清原理和主流程：
- 主路径的步骤顺序、分支条件，数据在各步之间如何流动（shape、dtype、所在内存的变化）；
- 背景知识和不常见术语用简短列表说明；
- GPU kernel 另按下文“GPU kernel 专项”展开。

### 4. 关键设计
逐条写：做了什么选择 → 为什么（事实依据并给出处；无依据时标“推测”并说明推理）→ 代价或限制。

### 5. 代码细节（文件/模块粒度）
- 按逻辑把代码分成段落章节；辅助函数单独一节，讲清功能、入参、返回值和内部原理。
- 冗长的主函数按逻辑分段，每段嵌入源码摘录并标注来源行号，在行尾或单独一行/多行加醒目的讲解注释（Python `# 【注】…`、C++ `// 【注】…`，其他语言用对应注释符）；无关部分折叠为 `# …（省略：xxx）`，不整文件粘贴。摘录只出现在讲解里，绝不回写源码。
- 遇到特殊指令、跨 lane 数据交换、数据加载/存储时配图（见“图示”）。

### 6. 依赖与调用关系
两张小表：直接依赖（符号、位置、在本代码中的作用）和调用方（位置、场景：生产/测试/benchmark、用法）；可附 mermaid 调用关系图。

### 7. 总结回顾
- 原理：设计背后若有数学原理（数值稳定、量化误差、复杂度、重排等价性等），给出稍详细的说明或搜索关键词；提及常见的替代做法及取舍（可联网查证，不编造链接）。
- 细节：写得好的地方及原因；写得不好的地方、可疑 bug、隐含假设、与注释不符之处（附位置，只指出不修改）；可在别处复用的组件。

## GPU kernel 专项（FlyDSL / HIP / Triton / 汇编）

在“执行流程与实现原理”和“代码细节”中额外讲清：
- **任务划分**：grid 每一维对应什么（M/N 块、expert、token 组、split-K 分片等），每个 CTA 负责输出的哪一块、如何遍历 K；CTA 内各 wave 如何分工协作（按 M/N 切分、按 K 切分后归约、生产者/消费者、ping-pong），每个 lane 负责哪些元素。
- **数据流**：global → LDS → VGPR → MFMA → 累加器 → epilogue → global 的每一级：tile 大小、buffer 个数（双缓冲/预取深度）、同步点（barrier、`s_waitcnt`）及其原因。
- **layout**：寄存器/LDS 中的数据映射回原 tensor 若不是简单线性连续（swizzle、padding、MFMA 操作数排布、打包的 fp4/fp8 及其 scale），必须画出 lane/thread → 元素坐标的分布图。
- **特殊指令**：MFMA（形状、操作数与结果布局）、直接写 LDS 的 buffer load、宽 LDS 读写、DPP / `ds_swizzle` / `permlane` / `readlane` 等跨 lane 交换、类型转换与打包指令：说明语义并配图。
- **参数与分发**：哪些是编译期常量（产生不同 kernel 变体），哪些是运行期参数；上层如何选择配置（调优表、启发式）。
- **资源与性能**：VGPR/LDS 用量与 occupancy；访存量和计算量的粗估（memory bound 还是 compute bound）；有实测数据时引用出处。

## 图示

- 对话中：流程和调用关系用 mermaid（flowchart / sequenceDiagram）；tile 划分、lane → 元素分布用 markdown 表格或代码块中的字符网格，标明坐标轴、单位和对应配置。
- 文档模式：示意图写成独立的 svg（手写、自包含、带 viewBox、文字标签和图例，用颜色区分 wave/lane/buffer），在 README.md 中用 `![说明](./xxx.svg)` 引用；简单流程也可用 mermaid。
- 图中的块大小、lane 数、坐标取自代码中的实际常量或配置，并在图注写明。

## 文档模式（仅在用户明确要求时）

触发：用户要求书面文档，如“生成讲解文档”“写成文档”“输出到 .explain”。
- 在源码旁创建与源码同名、以 `.explain` 结尾的目录：`moe.py` → `moe.explain/`；模块 `a8w4/` → 同级的 `a8w4.explain/`。主文件为 `README.md`，svg 等附件放在同一目录。
- 目录已存在时先读已有内容，问用户覆盖还是增量更新。
- README.md 开头注明讲解对象的路径和对应 commit（`git rev-parse --short HEAD`；有未提交改动时注明），正文使用完整的讲解结构：“执行流程与实现原理”不贴源码；“代码细节”覆盖全部辅助函数和主函数的每个段落。
- 除该目录外不写任何文件。完成后在对话中给出 3-5 条要点和 README.md 的链接。

## 交付前自检

- 每个结论都有出处，或已标为“推测”；
- 链接的行号与实际读到的内容一致；
- 覆盖了职责、执行流程和关键设计，依赖与调用方已按需追踪；
- 没有改动任何源码文件（文档模式只写了 `.explain/` 目录）。
