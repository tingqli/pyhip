# 实验日志 2026-11-18（b）：FionaZZ92 的 gfx942 MegaMoEV2 small-M 与 mega_small 对比

环境：8×MI300X（gfx942，304 CU，750 W），FlyDSL 0.3.2，torch 2.9.1+rocm7.2，MORI（heap 设为
8 GB）。形状：MiMo-V2.6-Flash EP8，H 4096、I 2048、256 个专家（每卡 32）、topk 8，token 均分到
8 个 rank；下文的 M 是每卡 token 数（FionaZZ92 的 M），tokens = 8M（本包调优表的 tokens）。
pyhip 基线：937370e（`mega_small` 刚提交）。运行于 2026-11-18 晚。实验目录：
`20261118_fiona_cmp/`。上一份日志：`log_20261118.md`（mega_small 本身）。

## 1. 来源与问题

- **来源**：FionaZZ92/aiter 28e6b92「feat(megamoe): backport gfx942 MiMo A8W4 decode to FlyDSL
  0.3.2」（父提交 108940c），配套 FionaZZ92/sglang 040fefd「feat(mimo): add opt-in MegaMoEV2 A8W4
  decode on gfx942 EP8」（`SGLANG_MIMO_MEGA_DECODE=1`）。内容：把 ROCm/aiter 的 MegaMoEV2
  small-input 单 kernel（`mega_moe_small_m.py`，gfx950，来源 ROCm/aiter PR7699）移植到 gfx942：
  - gfx942 没有 scaled MFMA，FP8×FP4 的 scaled MFMA 用软件模拟（`gfx942_scaled_mma.py`、
    `gfx942_operand_reuse.py`）；
  - OCP fp8 用软件转换；
  - 两套按 M 分档的 profile（`configs/model_configs/mimo_v26_flash_megamoe_gfx942_ep8*.json`）；
  - 每卡最多 512 tokens（`SmallMRuntime`，下文简称 Fiona）。
- **它自己发布的数据**（`docs/mimo_mega_decode.md`）：对 sglang 里的「MORI EPv1 + A8W4」，≤48 tokens/卡时
  快 33–37%，从 192 tokens/卡起慢 11–37%，10 个点的几何平均 1.039x；功能开关默认关闭。
- **问题**：本包的 `mega_small` 也是照着同一个 aiter kernel 做的（`log_20261118.md` §1–2）。要回答两件事：
  - 两个移植在算法上哪里不同；
  - 在同一台机器、同样的输入和权重、同一种计时方式下，各自多快。

### 2.2 在本机导入 FionaZZ92 的 aiter（不编译 CK）

- 直接 `import aiter` 会 JIT 编译 CK 模块，而浅克隆里没有 3rdparty 子模块。解决办法：
  - 设 `AITER_TRITON_ONLY=1`；
  - `sys.path` 加 `<checkout>` 和 `<checkout>/aiter/jit/utils`（`chip_info.py` 在顶层 import
    `build_targets`）；
  - `ref.make_weights` 要用 `aiter.QuantType / get_torch_quant / dtypes`，TRITON_ONLY 不导出这三个，
    从 `aiter.ops.enum` / `aiter.ops.quant` / `aiter.utility` 补上。
- `module_aiter_core` 第一次 import 时 JIT 编译了一次（17 s，不需要 CK）。FionaZZ92 的 kernel 一行没改。
- 同一个进程里只有这一份 aiter：pyhip a8w4 只在生成权重时用 aiter 的量化和 shuffle，这次用的就是 checkout 里的。

### 2.3 对比脚本 `20261118_fiona_cmp/cmp_fiona.py`

- 8 个 rank 在一个 spawn job 里（`a8w4.bench.dist`：gloo + nccl，MORI shmem），三种实现交错运行。
- **权重**：`ref.make_weights(32, 4096, 2048, seed=rank)` 生成原始 mxfp4。
  - pyhip：`prepare_weights` 得到 fd2。
  - Fiona：按 sglang 适配的方式 shuffle。
  - 两种布局各 8 份副本（`ref.weight_copies` / tuple clone）。
  - Fiona 每次调用前 `bind_weights(copy)`；预热时每份副本调用一次，顺便建好每份 W2 的 dispatch 表。
- **输入**：`make_routing(M, seed=7919·rank + M)`，uniform 路由，三种实现用同一份。
- **实例**：
  - `SmallMRuntime(max_tok_per_rank=512)`：profile 只在 mtpr 512 时生效。
  - `MegaMoeSmallEpA8W4`，bm 64（调优表在 128–1024 tokens 的选择）：8M ≤ 1024 时 tmax 1024；否则另建一个
    tmax 4096 的实例。后者超出了 solver 的上限，只是为了看同一设计在大 batch 时的表现。
  - `MegaMoeEpA8W4(max_tokens=512)`：8M ≥ 1024 时测，knob 用表里的（≤2048 tokens p16 l2 bcm22，以上 p16 l4
    bcm01；换法同 `moe_ep._mega_variant`）。
- **正确性**：每个点每种实现在副本 0 上 eager 调用一次，与 fp32 参考比较，取各 rank 最大值。
  - 参考用原始 mxfp4 权重，x 和中间结果都不量化；
  - 指标为 cos 差和相对 L2，并检查输出全部有限；
  - eager 调用限时 120 s（超时直接退出，以防跨卡等待卡死整个 job）。
- **计时协议**：
  - `cold`：kernelkit 的方式。每次调用前 flush L2、换下一份权重副本、host barrier、GPU spin、MORI 设备
    barrier；取最慢的 rank；每次迭代按 ABBA 交错，30 次迭代取中位数；`fiona#2`（Fiona 再测一遍）作为噪声带。
  - `graph8`：一个 graph 里连续 8 次调用，第 i 次用副本 i（相当于 8 层）；每轮回放 20 次，每次调用的时间 =
    回放时间 / 8；取最慢的 rank，7 轮（ABBA）的中位数。
  - `graph8w`：同上，但 8 次都用副本 0，即 FionaZZ92 自己的计时方式。

## 3. 算法对比

### 3.1 相同的部分

都是一次 launch 做完整层，流程相同：

1. 量化 x，用目的卡上的 system atomic 取固定槽位，把行直接写过去；
2. 目的卡等所有源卡的完成信号，再建 m-tile 表；
3. GEMM1 / GEMM2 按 XCD 分段取 unit，GEMM2 等它所在 m-tile 的 GEMM1 全部完成；
4. GEMM2 把乘过路由权重的行写回源卡 combine 输入的 (token, slot) 位置；
5. 每个 rank 自己把 topk 行加起来。

两者都对 CUDA graph 安全（设备侧 epoch），都能把 topk id -1 当作「不路由」。

### 3.2 不同的部分

| 部分 | Fiona（`SmallMRuntime`，`mega_moe_small_m.py`） | pyhip `mega_small`（`kernels/ep_mega_small.py`） |
|---|---|---|
| grid / 资源 | 304 CTA × 256 线程（4 wave），gfx942 上 grid_mult 限 1；388 VGPR（tn128）/ 476（tn256），tn128 有 3 个 spill（VGPR + SGPR 合计），LDS 29–37 KB → 每 SIMD 1 个 wave | 304 WG × 512 线程（8 wave）；224 VGPR，LDS 41.5 KB → 每 SIMD 2 个 wave |
| 角色 | 入口 ticket（agent atomic）：ticket 0 = owner，1..64 = producer（dcu 64），其余 consumer；做完角色的 CTA 都进 GEMM | block id < 16 = producer；所有 WG 都做 GEMM |
| 调用边界 / epoch | ticket 的代数 = epoch；owner 复位各 XCD 的 work 计数器、翻转 parity、算本次 expected，release 后开 gate；consumer 先等 gate；producer 预取并量化第一路后再等 gate | `ctl[SC_EPOCH] + 1`，最后一个 WG 写回；没有 gate（rank 进入第 N+1 次调用时，第 N 次的所有行已经到达它） |
| 量化 + dispatch | 每一路 (token, k) 一个 wave：读 bf16 行，量化成 MXFP8（1×32 E8M0，OCP e4m3，gfx942 上由 `fp8_ocp_bits` 软件转换）；同一 token 量化 topk 次；目的卡 `running[e]` 上 system atomic 取槽，写 4 KB 行 + 128 B scale + 权重 + srcmap | 每个 token 一个 wave：lane 0–7 一次发出 topk 个槽位 atomic，行在 atomic 往返期间读入；只量化一次（FNUZ fp8，每 128 列一个 f32 scale，硬件 cvt）；写到 topk 个目的卡 |
| 源卡完成信号 | `group_done` 计数，最后一个 producer CTA 给每个目的卡写 `count_done[parity][src] = expected`（parity 双缓冲） | 每个 producer 的 store 完成后，往每个目的卡的 `done[me]` 加 64/P；目的卡等到 epoch·64 |
| 建 tile 表 | owner 等 8 个源卡，读 32 个计数，写 sorted_expert / tile_row_base / tile_rows（global），复位计数；发布 i64 plan 字（epoch<<32 \| num_valid \| cached_w 位 \| fp8_rows 位）。每个 XCD 第一个取到工作的 CTA 等 plan 后做 agent acquire（L2 invalidate）并转发，同 XCD 的其他 CTA 等转发后丢 L1 | 每个 WG 等 done，用 system load 读 32 个计数，wave 0 做前缀和，表建在自己的 LDS 里；不发布、不 invalidate |
| 固定槽位 | 每个专家 ceil(8·mtpr/32)·32 = 4096 行（mtpr 512/卡）：rx 512 MiB/卡，combine 输入 32 MiB | 每个专家 tmax 行（tmax 1024，所有卡合计）：rx 128 MiB，combine 输入 64 MiB |
| GEMM1 unit | m-tile（32 行）× 128 行 W1（gate/up 交错，出 64 列中间结果），256 KB W；≤12 tokens/卡时 tn256（512 KB） | m-tile（bm 64，按有效行数跑 16/32/64 行变体）× 256 行 W1（出 128 列中间结果），512 KB W |
| GEMM2 unit | m-tile × 256 列输出（≤12 tokens/卡时 128 列），K 2048，256 KB W | m-tile × 256 列输出，256 KB W |
| W / A 流水 | W 提前 1 个 K-step（`do_tile_la`，LA = 1）；NATIVE_B 时每 lane 每个 pack 发 4 条 dword load；A 走 LDS 双缓冲 | W 从 HBM 直接流进 VGPR，提前 PF = 2 个 K tile；A 走 swizzle 的 LDS；SCH 3（每个 tile 最后一步的 MFMA 推迟到下一 tile 的 barrier 之后） |
| MMA 数值 | MXFP8 A × MXFP4 W，每个 K32 缩放一次（§3.3） | fd2 W × fp8 A（每 128 K 一个 f32 scale，§3.3） |
| 工作分配 | 每个 XCD 一个计数器，取 GEMM1 unit 空间连续的 1/8（切点对齐到 4 个 n-tile），然后取同位置的 GEMM2 段；不窃取 | 每个 XCD 一段 GEMM1 + 一段 GEMM2（同一批 m-tile）；本段取完后去其他 XCD 窃取（先用普通 load 探测） |
| GEMM1 → GEMM2 | 每个 m-tile 计数，最后一个 unit 写 `g2_ready[m] = epoch`（agent release）；被切开的 m-tile 由两个 XCD 各自 release；GEMM2 等到相等后丢 L1 | 每个 m-tile 计数（SC_TILE），GEMM2 等到 ≥ NG 后丢 L1；a2 写穿（sc1） |
| GEMM2 epilogue | 经 LDS 做 CShuffle，乘路由权重，写 BF16 行到源卡的 combine 输入 [token·topk + k]（uncached heap）。重负载 rank（路由行 ≥ 4608，或热点专家 ≥ 256 行）动态改发 FP8 行 + E8M0 | 乘 channel factor 和路由权重 → bf16 LDS tile → 每行一个 wave，写到源卡的 `cin[token, slot]` |
| combine | 每个 CTA 取 ticket；最后一个 CTA 给每个 peer 写 flag（带格式位）；最后 min(grid, 256) 个 CTA 等齐所有 flag、丢 L1，按 1 KB 一块规约 topk 行（f32 累加 → bf16） | 两级计数；最后一个 WG 复位计数器、run[] 和 epoch 后给每个 rank 写 cflag；WG b < n 等齐所有 cflag，规约 token b, b + 304, …（一个 WG 一行 8 KB） |
| 运行时切换 | plan 字里的 cached_w 位（路由行 ≥ 2560，或热点专家 ≥ 256 行）选择 W 走 cache 的 GEMM body；按阈值推算，418 / 512 tokens/卡（每卡约 3344 / 4096 行）时已切换。fp8_rows 位见上。按每卡 token 数在 3 个编译好的 config 中选 | 无：bm 是编译期 knob，由表选；大 batch 交给 `mega` |

### 3.3 GEMM 内核：模拟的 scaled MFMA 与 fd2

**Fiona**（sglang env：MMA fp8，UNPACK reuse，OPERANDS native_ab_early）：

- **A**：MXFP8 字节是 OCP e4m3，在 gfx942 上直接当 FNUZ 用。普通值的同一字节在 FNUZ 里只有一半大，乘子里补 2 倍。
  0x80（OCP 的 −0，FNUZ 的 NaN）要清掉，每个 dword 3 条位运算。
  NATIVE_A 时 A 从 LDS 按 MFMA 的布局读（每个 K32 4 次 8 B），不用 ds_bpermute。
- **W**：MXFP4 经 `unpack_fp4x8_lut` 的 v_perm 查表解成 FNUZ fp8。每个 N/K tile 解一次，M 方向的 fragment 共用（reuse）。
- **每个 K32 的计算**：
  1. MFMA 16×16×32 写进一个清零的累加器；
  2. `acc[i] += partial[i] · 2^(ea_i + eb − 253)`，其中 2^(ea−127)·2^(eb−127)·2 的 2 补的是 FNUZ 的一半；
  3. ea 是 A 每行的 E8M0（ds_bpermute 取），eb 是 W 每列的 E8M0。early 模式在 MFMA 之前算好 4 个乘子。

**pyhip**（`_kloop._make_core`）：

- **W 是 fd2 形式**：
  - 每个 32-K 组的 E8M0 与该输出通道最大 E8M0 的差，折进 fp4 → fp8 解码的 LUT（`_fp8_lut_predelta`）；
  - 比通道最大值小 ≥ 12 的组解成 0；
  - 通道最大值的因子在 epilogue 乘一次（`_channel_factor`）。
- **A**：FNUZ fp8，每 (行, 128 K) 一个 f32 scale。K 循环里每过 128 K，把累加器乘一次 s[g−1]/s[g]（LDS 里的 ratio 表）；
  epilogue 再乘最后一个 scale。
- 结果是一条 MFMA 累加链，没有每 K32 的乘加。

## 5. 机理：为什么慢 2–3 倍

**资源**（`prof isa`，空 cache 编译时 dump）：

| kernel | vgpr | agpr | sgpr | spills | LDS B | WG size | waves/SIMD (VGPR) |
|---|---:|---:|---:|---:|---:|---:|---:|
| Fiona tn128 wpe1（≥128 tokens/卡） | 388 | 0 | 96 | 3 | 37264 | 256 | 1 |
| Fiona tn128 wpe2（24–96） | 388 | 0 | 96 | 3 | 37264 | 256 | 1 |
| Fiona tn256 wpe1（≤12） | 476 | 0 | 92 | 0 | 29072 | 256 | 1 |
| pyhip mega_small bm64 | 224 | 0 | 88 | 0 | 41568 | 512 | 2 |

（kernel 全名见 `isa_resources_loop_mix.txt`；wpe2 的 hint 没有改变寄存器数。）

**内循环指令**（`loop_mix.py`：从标签到回跳的循环体，取含 MFMA 的最内层循环）：

| 循环 | 每 K32 每 wave 的 fragment（M × N） | MFMA / 迭代 | VALU / MFMA |
|---|---|---:|---:|
| Fiona GEMM1 tn128（nt / cached 两份） | 2 × 2 | 32 | 26.8 |
| Fiona GEMM2 bn256（两份） | 2 × 4 | 64 | 27.4 |
| Fiona GEMM1 tn256（≤12 tokens/卡） | 2 × 4 | 64 | 26.4 |
| Fiona GEMM2 bn128（≤12） | 2 × 2 | 32 | 30.2 |
| pyhip gemm1 bm64 | 4 × 2 | 256 | 2.89 |
| pyhip gemm1 bm32 | 2 × 2 | 128 | 5.23 |
| pyhip gemm1 bm16 | 1 × 2 | 64 | 9.89 |
| pyhip 第 1192–8740 行的循环（推测是展开的 gemm2 与循环外的代码） | – | 899 | 5.45 |

- 形状相同的 GEMM1（每 K32 2 × 2 个 16×16 fragment：Fiona tn128 对 pyhip bm32），每条 MFMA 配的 VALU 是
  26.8 对 5.23，约 5 倍。
- Fiona 每条 MFMA 的构成：
  - 3.1 条 v_perm（fp4 解码等）；
  - 4.6 条 f32 乘加（缩放后累加）；
  - 13–16 条整数 / 位运算（清 −0、拼指数、地址）；
  - 3 条 mov（清零累加器等）。
  括号里的归类是按源码推断的。pyhip 的 gemm1 循环是 3 次迭代的 K 循环，每次迭代 4 个 K tile × 8 步 ×
  2·MR 条 MFMA，与表中的 MFMA 数吻合。

**计数器**（M = 48，每次调用的均值，`counters_m48.txt`；cycle 类计数器不可用，原因见 §8）：

| 计数器 | Fiona | pyhip mega_small |
|---|---:|---:|
| SQ_INSTS_VALU | 135.72 M | 20.86 M |
| SQ_INSTS_MFMA | 3.15 M | 1.68 M |
| SQ_INSTS_SALU | 11.71 M | 2.58 M |
| SQ_INSTS_LDS | 3.05 M | 0.95 M |
| SQ_INSTS_VMEM_RD | 16.13 M | 1.41 M |
| TCC_EA0_RDREQ_sum | 3.40 M | 3.44 M |
| VALU / MFMA | 43.1 | 12.4 |
| VALU / SIMD（304 CU × 4） | 112 k | 17 k |

- **DRAM 读请求相同**（3.40 M 对 3.44 M）：两边读的 W 字节一样，不是带宽问题。
- **Fiona 的 VALU 是 6.5 倍**。每 SIMD 112 k 条，按每条 wave64 VALU 至少占 4 个周期，约 45 万周期，
  在 1.05–1.4 GHz（750 W 下的频率）下是 0.32–0.43 ms，与实测的 418.6 us 同量级。每 SIMD 只有 1 个 wave，
  没有别的 wave 能把这段时间与访存或 MFMA 重叠。pyhip 每 SIMD 17 k 条（约 7 万周期，≈ 50 us），不是它的瓶颈：
  它的瓶颈是 W 的流入和每个 unit 的预取填充（`log_20261118.md` §3.3）。
- **MFMA 多 1.9 倍**：48 tokens/卡时每个专家约 12 行，Fiona 总按 32 行的 tile 算，pyhip 跑 16 行变体。
- **VMEM 指令多 11 倍**：NATIVE_B 每 lane 每个 pack 发 4 条 dword load，此外还有自旋等待时的 load。
- **不是协议开销**：1 token/卡（每卡约 7 个活跃专家）时比值 2.86x，与 512 tokens/卡时同量级。

## 6. 结论

- 两者是同一设计。FionaZZ92 的 gfx942 移植保留了 gfx950 的数值（MXFP8 激活，每 K32 一个 E8M0 缩放），scaled MFMA
  靠软件模拟。
- 后果：它的 GEMM 循环每条 MFMA 配约 27 条 VALU，又只有每 SIMD 1 个 wave，整体受 VALU 发射限制。
  在 1–512 tokens/卡上，它比 pyhip 最快的方案慢 2.15–2.86 倍（cold），在 graph 里慢 2.3–3.3 倍。精度相当。
- 它发布的收益是相对一个 629–661 us 的 MORI 基线，换成本包的 MORI 路径（186 us）就不成立。
- **结论：本包不改**，`mega_small` 仍是 decode 段的 solver。它的 GEMM 和协议都没有可搬的。

## 7. 可借鉴 / 后续方向（按收益）

1. **mega_small 的 tmax 提到 2048**（pending）。
   - 1536 tokens 时 mega_small 比 mega 快 4.8%（cold 284.6 对 299.0 us）/ 5.7%（graph8 270.3 对 286.7 us）；
     2048 tokens 时持平（369.2 对 368.2 us），与 `log_20261118.md` §3.4 的 ab4 一致。
   - 这只是一次扫描、一个路由样本中的一个点，需要在 1280 / 1536 / 1792 tokens 用 `kernelkit ab` 复测。
   - 现在的表在 1024 和 2048 之间没有点：1536 tokens 的调用会落进 2048 的点，选 mega。
   - 可与 `log_20261118.md` §6 的「跨 unit 的 W 预取」一起做。
2. **mega_small 的运行时 W cache 开关**（idea）。
   - 3344 / 4096 tokens 时，mega_small（t4096，W 走 nt）比 mega（bcm01）慢 6.1% / 13.0%（cold）。
   - Fiona 的做法：plan 字里一位按每卡路由行数选择 W 走 cache 的 GEMM body。
   - 只有把 mega_small 扩到 2048 tokens 以上才有意义。
3. **重负载 rank 发 FP8 combine 行**（idea，低）。GEMM2 scatter 的字节减半；uniform 路由在 ≤512 tokens/卡时不会触发，
   只对热点路由有意义。

不搬的部分：

- MXFP8 激活加模拟的 scaled MFMA：§5 的代价；
- 每路一个 wave 的量化；
- owner 建表后发布 plan，再按 XCD 做 L2 invalidate：pyhip 每个 WG 自己建表，少一跳，不需要 invalidate；
- 不窃取的 XCD 分段。

## 8. 反思

- **花时间最多的一步**：在同一进程里导入另一份不带 CK 编译的 aiter。做法是 `AITER_TRITON_ONLY=1`、加
  `aiter/jit/utils` 路径、补三个顶层导出，已写在 `cmp_fiona.py` 开头。以后对比其他 aiter 分支时可以照用。
- **先复现对方发布的数**（graph8w 在 0..−13% 以内），再看对比结果：确认差距不是 harness、权重布局或调用方式造成的。
- **`a8w4.prof counters` 的解析崩溃**：rocprofv3 对 8 进程 job 的 CSV 里有 `Kernel_Name` 为空的行。
  4 遍 profiling 已经跑完，`parse_counters` 在 `re.search(kernel, None)` 处崩了，于是手工汇总。
  修法：`name = r["Kernel_Name"] or ""`，这里没有改。
  另外，kernel 自旋等待其他 rank，profiler 又逐个 dispatch 串行化，所以 cycle 类计数器
  （SQ_BUSY_CU_CYCLES、SQ_WAVE_CYCLES 等）没有意义，只用了指令数和请求数。
- **跑测期间另一个会话改了 `megamoe.py`、`moe_ep.py`、`kernels/_protocol.py`**（mega_large 的 WIP）。核对过：
  - `git diff` 只有新增；
  - `ep_mega_small.py` 和本脚本用到的类、`_mega_variant` 都没变；
  - 三个 job 里 mega_small 的数相差 ≤ 2.1%（§4.3）。
  所以结果有效。
- **跨 job 的比较**（aiter 默认模式）用 mega_small 作锚，只在差距远大于锚的漂移时下结论。
