# 实验日志 2026-11-18（c）：EP 整层的大 batch 单 kernel（megamoe large）

环境：8×MI300X（gfx942，304 CU，750 W），FlyDSL 0.3.2，torch 2.9.1+rocm7.2，MORI（uncached
symmetric heap，默认 4 GB）。形状：MiMo-V2.6-Flash EP8，H 4096、I 2048、256 个专家（每卡 32）、
topk 8，token 均分到 8 个 rank。计时一律用 kernelkit（L2 flush + 8 份权重副本轮换，各 rank 对齐
后取最慢的 rank，ABBA 交错，`<base>#2` 为噪声带）。实验目录：`20261118_mega_large/`。

## 1. 来源与动机

- **来源**：ROCm/aiter `aiter/ops/flydsl/kernels/mega_moe/mega_moe_large_m.py`（MegaMoEV2 的
  large-input 路径，gfx950）：dispatch、GEMM1、GEMM2、combine 融合成一个 persistent kernel
  （quant 单独一个 kernel）；dispatch 为每个目的卡规划行、按 tile 发布，GEMM2 只等喂它的 GEMM1
  tile；combine 把行用 fp8 传回源卡，由源卡求和。
- **动机**：原表 ≥2048 tokens 选 `mega`（5 次 launch：quant / prep / plan / mega / finish，两次
  跨卡同步）。`test_a8w4_megamoe_ep8.py -t 2048 8192 32768` 的分解：prep + plan + finish 在
  2048 tokens 时约 49 us（389 us 中），32768 时约 113 us；mega kernel 本身比单卡 ep3k 的纯计算
  慢 19–26%。

## 2. 实现（gfx942 上的改编）

`kernels/ep_mega_large.py`（`megamoe.MegaMoeLargeEpA8W4`，`moe_ep` solver `mega_large`），设计见
kernel 文件的模块文档。每次调用一个 kernel：grid = 304 个 WG（每 CU 一个，512 线程，全部驻留），
WG 0 是 planner，[1, P] 是 producer，其余做 x 量化；之后所有 WG 去取 GEMM unit。

| 部分 | aiter（gfx950） | 本包（gfx942） |
|---|---|---|
| GEMM | MXFP8 A × MXFP4 W | `_kloop._make_core` 的 a8w4 tile（fd2 W 流进 VGPR，fp8 A 经 LDS），128 行 m-tile，行数变体 32 / 64 / 128 |
| x 量化 | 单独的 quant kernel，MXFP8（每 32 列） | 同一 kernel 里，每个 token 一个 wave；knob `qx`：每行一个 scale（`a8w4_moe` 的做法，gemm1 不用逐组重缩放）或每 (行, 128 列) 一个（gemm1 每 128 K 重缩放累加器，同 `ep_mega`） |
| 计数交换 | dispatch 规划 | producer 扫描路由、LDS 计数器给出段内序号，段大小写进目的卡的计数矩阵，再加目的卡的 `cdone[me]` |
| 行布局 | 每个目的卡规划、按 tile 发布 | 目的卡的 planner 等齐 8 个源的计数后排布（专家顺序，每个专家补齐到整 m-tile，专家内的源从本卡开始轮转：第一个 m-tile 多是本地行），把段起点写回各源卡 `pbase`，发布 m-tile 表和 `pflag` |
| dispatch | payload 分块（`payload_chunk_rows`） | producer 每个 wave 一次发 8 路（先发全部 load 再发 store），`vmcnt(0)` 后给目的卡对应 m-tile 的 `tready` 加行数（最多跨 2 个 tile） |
| 工作分配 | `work_shards` 个 ticket 计数器，unit m-tile 优先 | 8 个分片（按 XCD），unit u 属于分片 u mod 8；gemm1 unit（m-tile 优先）在前，gemm2 在后；本分片取完后去别的分片取剩余（先普通 load 探测） |
| GEMM2 等待 | 等喂它的 GEMM1 tile | 等该 m-tile 的 I/128 个 gemm1 unit（每 m-tile 一个计数行） |
| combine | fp8 行传回源卡，源卡求和 | knob `comb`：`add` = BF16x2 atomic 直接加进源卡 `out[token]`（同 `ep_mega`）；`fp8` = 每 (行, 128 列) 一个 f32 scale 的 fp8 行写进源卡 `cin[token, slot]`，结束时每个 WG 汇总自己的 token（按槽位顺序，逐位确定） |
| 结束 / epoch | — | 两级计数，最后一个 WG 给所有卡发 `fflag`、复位计数器、写回 epoch（`ctl[LC_EPOCH]`）；graph 回放安全 |

容量：每卡最多接收 `s_cap` = 2·tcap·topk + 32·128 行（均匀路由平均值的 2 倍），超出的路由被丢弃
（`rows_needed()` 可查）。symmetric heap 在 tcap 4096 时 0.47 GB。ISA：VGPR 235（`qx` 1：247），
SGPR 106，SGPR spill 8（`comb` fp8：13，全部 spill 到 VGPR lane），无 scratch，LDS 64 KB，
每 SIMD 2 个 wave。

## 3. 实验

### 3.1 正确性（`check_large.py`，`pytest a8w4/tests/test_a8w4_megamoe_ep8.py -k large`，`kernelkit check --graph`）

- 均匀 / 热点路由；每卡 0、1、37、300、999、1024、4096 tokens，idle rank、全部 idle、单 token；约 1/16
  槽位为 -1；silu / situv2；`comb` add / fp8，`qx` 0 / 1，producers 16 / 32：与按 kernel 自己的
  fp8 x 算的参考相比 cos 差 0.6–1.0e-5（`add`），3.3e-4（`fp8`），无 NaN。
- 超出 `s_cap`：所有 rank 的 token 都发往 rank 0 的专家 0–7（8 倍均值），被丢的整段路由必须
  什么都不加：pytest 的 `_check_large_overflow`。这一项查出 fp8 combine 的 bug（见 3.5）。
- CUDA graph：pytest 的回放序列（两个 graph 交替、中间夹另一个 kernel 变体的 eager 调用、
  padding 行为 -1）通过；`kernelkit check --graph`（`check_graph.md`）：capture + 回放与 eager 的
  差 ≤5e-6（`add`：BF16 atomic 的顺序不定），`fp8` combine 重复调用、回放都逐位相同。

### 3.3 时间线（`pre_cleanup.diff` 里的编译期开关 TL：每个 WG 在阶段末和每个 unit 前后写 `s_memrealtime`；`timeline_large.py`）

- **2048 tokens**（rank 0，bcm01）：plan 8.5 us，dispatch 结束 61–72 us，gemm1 unit 中位 106 us
  （此时每个 m-tile 约 64 行），gemm2 unit 59 us，每个 WG 第一个 gemm1 unit 等行中位 10 us
  （p90 33 us），unit 循环 307–335 us 结束，e2e 345 us。均匀分摊的 GEMM 约 280 us/WG。
- **8192 tokens**：dispatch 结束 169–185 us（P 32：146–165，P 8：259–287），gemm1 unit 113 us、
  gemm2 74 us，每 WG 等行合计 51 us，e2e 859 us。
- **32768 tokens**：dispatch 结束 608–643 us，GEMM unit 约占每个 WG 时间的 92%，各 rank 的 unit
  循环结束时间相差 100–170 us（最慢的 rank 决定 e2e）。
- gemm1 unit 64 行和 128 行一样慢（约 106 us），与 ep3k l128 的单卡每 tile 时间（约 102 us）一致：
  unit 受 W 的读取和 fd2 解码（VALU）限制，与行数无关。
- dispatch：8192 tokens 时每卡发 32 MB（约 28 MB 跨卡），约 160 us，即约 175–200 GB/s/GPU；MORI
  dispatch 在同样条件下约 180 GB/s（8192）、240 GB/s（32768）（`test_a8w4_mori_ep8.py`）。P 翻倍只快
  约 15%：瓶颈是 XGMI 链路的实际吞吐，不是 producer 的 wave 数。
- combine 的上限（调试开关 LCOMB：远端 atomic 改为加进本卡，结果错误，只用于量时间）：e2e
  −2.6%（2048）、−6.5%（8192）、−11.8%（32768）。G2 阶段的远端 BF16 atomic 约 230 MB/卡
  （32768），在结尾排队，`vmcnt(0)` 要等它们排空。

### 3.5 精度：x 的量化粒度（`precision_qx.py`）与 fp8 combine 的丢弃路由

`moe_ep_ref` 把 x 按 (行, 128) 量化（同 `mega` / `mori`）。与**不量化 x** 的 fp32 参考比（每卡
256 / 1024 tokens，`--outliers`：1/64 的通道放大 30 倍，模拟 LLM hidden state 的离群通道）：

| act | x | 每行一个 scale | 每 (行, 128) 一个 |
|---|---|---:|---:|
| silu | 高斯 | 1.21e-3 | 1.16e-3 |
| silu | 有离群通道 | 1.15e-3 | 6.2e-4 |
| situv2 | 高斯 | 4.2e-3 | 3.9e-3 |
| situv2 | 有离群通道 | 9.0e-3 | 3.7e-3 |

- 高斯 x 时两者一样准；有离群通道时每行一个 scale 差 2–2.4 倍。
- 对 `moe_ep_ref` 的 cos 差是两种量化噪声之和：每行 scale 在 silu 是 1.8e-3（fp8 combine 2.2e-3），
  在 situv2 是 7.3e-3，超过 5e-3，被调优表判为 BAD（`tune_v1_situv2_xrow_bad.log`）。所以 `qx`
  做成 solver 的 knob（`xrow` / `x128`），由表按 act 选：silu 选 `xrow`（与 `a8w4_moe` 相同的
  x 量化），situv2 只能选 `x128`。（后来改成了问题维度 `x_quant`，见第 7 节。）
- **bug**：`comb` fp8 时，超出 `s_cap` 被丢弃的路由没有行发回来，combine 却照样读它的 `cin` 槽位，
  加进去的是上一次调用的行（rows add 0 只对 atomic combine 成立）。修复：producer 发现目的卡放不下
  的段时（setup 时 ballot 出一个标志），把这些路由在本卡的 `cin` 槽位清零（`drop_slots`，只在溢出时
  运行）。pytest 的溢出用例在去掉修复时失败（cos 差 0.26–0.38），加上修复通过。

## 5. 反思

- 精度要按调优表的参考和对不量化 x 的真值两种口径看：只看 kernel 自己的 fp8 x 参考（check_large、
  pytest），每行 scale 的 situv2 版本处处通过，到 tune 时才被 `moe_ep_ref` 拦下。新的量化方式应当
  在实现时就跑一遍 op 的参考（`kernelkit ab` 的 cos ref 列已经显示 1.8e-3，当时只当作 silu 的
  固定偏差）。
- 时间线比扫 knob 更快定位：dispatch 的吞吐上限（XGMI，加 producer 无用）、gemm1 unit 与行数无关、
  combine 的 atomic 在结尾排空，三条都直接决定了后面哪些 knob 值得做。
- 去掉实验开关前先把带开关的版本存成 diff（`pre_cleanup.diff`），时间线脚本还能复现。
- fp8 combine 读的是「每个槽位都有人写」的输入，任何会让某路不发送的路径（丢弃、负 id）都要
  在读端或发端补零；atomic combine 没有这个问题，所以第一版测试没覆盖到。

## 6. 后续方向（按收益）

1. dispatch 去重：一个 token 发往同一目的卡的多个专家时只发一行（约 −34% 的 dispatch 字节），
   在目的卡按专家复用；dispatch 在 8192 tokens 时约 160 us。
2. 各 rank 结束时间相差 100–170 us（32768）：按路由给各 rank 的 unit 数做负载估计，或者允许
   跨卡帮忙（需要 W 在别的卡上）。
3. `qx` 1 的重缩放（+3–8%）：situv2 必须用它。先用时间线 / 计数器分清开销在 K 循环的 pk_mul
   还是每个 unit 开头建 ratio 表（32 组 × 128 行的除法），再决定怎么省。
4. sglang 接入：`mega_large` 是第四套跨卡协议（`moe_ep_sglang.md`），与 `mega` / `mega_small` /
   `mori` 都不能混用；prefill 和 decode 走不同 solver 时，两套 symmetric buffer 都要常驻。

## 7. 后续：x 的量化粒度改成 `moe_ep` 的问题维度 `x_quant`（2026-11-19）

### 7.1 为什么是 dim 而不是 knob

x 每行一个 scale 还是每 (行, 128 列) 一个，是调用方决定的输入格式：模型的量化方案决定它，
MORI 的 blockwise fp8 dispatch 也决定它。它不是 solver 的实现细节。把它做成 `mega_large`
的 knob `qx`（3.5、4）有两个问题：

- 表替调用方选了量化方式：silu 选了每行一个 scale，而有离群通道时这种量化的误差是另一种的
  2–2.4 倍（3.5）。
- 参考只能按一种量化：`moe_ep_ref` 固定每 128 列一个 scale，每行 scale 的配置与参考的差是
  两种量化噪声之和，situv2 因此超出容差。

判断标准：一个参数改变结果的口径（与参考比的是什么），它就是 dim；只改变速度，才是 knob。

### 7.2 接口

- `moe_ep_problem` 加 dim `x_quant`，取值为 `_protocol.X_QUANTS` = (`per_1x128`,
  `per_token`)，默认 `per_1x128`。
  - problem id 变成 `<group>-<act>-<x_quant>`；`EP_TUNING` 的 key 加 `x_quant`。
  - `moe_ep_ref` 用 `ref.quant_x(x, x_quant)` 量化 x。per_token 走 `quant_fp8_rows`：每行
    amax / 240。
- 哪些 solver 支持：
  - `mega`、`mega_small`、`mega_large` 两种都支持。
  - `mori` / `mori_eager` 只支持 `per_1x128`（MORI 的 blockwise fp8 dispatch）。per_token
    时 assert，表里记为 n/a。
- `mega_large` 去掉 knob `qx`，配置从 8 个减到 4 个（`comb` × `bcm`）。

### 7.3 kernel

三个 mega kernel 和 mega 的 quant kernel 统一用编译键 `QX`：

- QX 1：每 (行, 128) 一个 scale。这是默认值，kernel 名字和 ISA 与改动前相同。
- QX 0：每行一个 scale，kernel 名字加 `_xrow`。

各 kernel 的改动：

- **mega 的 quant kernel**：QX 0 是另一个 kernel `a8w4_megamoe_quant_h{H}_xrow`。每个
  token 一个 wave；CH 个 chunk 的 amax 经 6 步 shuffle 得到行最大值；scale 写成 [T]。
  `launch` 按 QX 选 kernel。
- **`ep_mega`**：producer 每行只发 1 个 scale（lane 0）。gemm1 不重缩放（hook 为 None）：
  行 scale 读进 LDS 的 fin 槽位，在 epilogue 里乘。
- **`ep_mega_small`**：quant 时求整行的 amax；gemm1 的处理同 `ep_mega`。
- **`ep_mega_large`**：原来就有 QX 0 / 1，只把默认值改成 1，名字后缀由 `_qx128` 改成
  `_xrow`。`pre_cleanup.diff` 按改后的 kernel 重新生成。

### 7.4 验证

- **默认路径没有动**：QX 1 的 ISA 与改动前逐字相同。比较的是 mega、mega quant、
  mega_small bm32 / bm64 与 HEAD 的 `prof isa` dump。
- **QX 0 的资源**：VGPR 为 mega quant 92、mega 229、mega_large 235、mega_small 200 / 220；
  没有新增 spill。
- **pytest**：`pytest a8w4/tests/test_a8w4_megamoe_ep8.py` 6 passed（343 s）。
  - 三族都加了 per_token 用例：mega 的不均匀 / 空 rank；mega_small 的 bm × x_quant；
    mega_large 的 knob 组合与 graph 回放序列。
  - 与同样量化的参考相比，cos 差约 8e-6（mega、mega_large），2.7e-6–9.2e-5（mega_small）。
- **verify**：`kernelkit verify … -t 20 100 300 1000 1500 3000 6000 20000`
  （`tune_xq_verify.log`）。4 个 problem 都按自己 x_quant 的行选配置，cos ≤ 4.8e-4。

### 7.6 反思

- 量化方式这种改变结果口径的参数，应当在问题定义里、在参考里出现。做成 knob 时，表会替调用方
  选一个更快但精度不同的方案，参考也只能对齐其中一种。第一版只把 situv2 的 BAD 当作「这个 knob
  在 situv2 上不可用」处理，没有追问参考为什么只有一种。
- 新加的选项不改默认值（QX 1、名字不变），就能用 HEAD 的 ISA 逐字比较，直接证明默认路径
  没有被碰到。
- 偶发的慢点只出现在一个族、几个相邻点上，重调一次就消失（这次是 mori 慢 1.3–4.6 倍）。只看
  「每点最快」的比较发现不了它；逐配置与上一版表比较（变化超过 ±20% 的行）才能找出来。
