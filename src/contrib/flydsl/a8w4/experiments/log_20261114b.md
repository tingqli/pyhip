# 实验日志 2026-11-14（b）：a8w4 MoE 的 TP / EP / mega，重点 1024–32768 tokens

环境：8×MI300X（gfx942），FlyDSL 0.3.2，torch 2.9.1+rocm7.2。形状：MiMo-V2.6-Flash，H 4096，topk 8；
TP8 = I 256、256 个专家；EP8 = I 2048、每卡 32 / 256 个专家。计时一律冷 L2、取中位数；TP 实验在同一进程内交错多轮，megamoe 扫描每个设置单独一个 job（为此另做了 ABBA 复测）。
上一份日志：`log_20261114a.md`（EP gemm 配置扫描，无收益）。

## 3. 实验

### 3.1 split-K gemm1（`20261114_splitk_gemm1/`）

- **做法**：在 EP gemm1 上加 split-K（`ep_gemm_sk.py`，对 `kernels/ep_gemm.py` 的改动见 `ep_gemm_sk.diff`）。valid tile ≤ sk_tiles 时把 K 切成 sk 份，各份用 fp32 atomic 累加，最后一个到达的 WG 做激活和 q8 量化。
- **EP（每卡 1 个本地专家）**：T=1 34.6 → 26.5（sk4p2t64）/ 25.0 us（sk8p1t64）；T=2 −16% / −20%；T=4 −14% / −8%；T ≥ 8 在 +1–2% 的噪声内。
- **TP**：用 tp_prep + split-K EP gemm1 + tp_gemm2，最终数据见 3.3（T=1 −56%）。
- **EP gemm1 跑 TP 形状，T=1024**：与 tp_gemm1 持平（约 113 us，约 2.4 TB/s，相当于 HBM 带宽的 50%），没有收益。
- **限制**：ep_gemm2 不能跑 TP 形状（需要 I / arb ≥ 8）。

### 3.2 TP 融合 prep：v1 → v2a → v2b → v2c（`20261114_tp_prep/`）

目标：一次 launch 完成全部 256 个专家的排序、x 行量化和 out 清零，替代 aiter `moe_sorting` + `quantize_rows`。

**v1（`tp_prep_v1.py`）**
- 结构：沿用 ep_prep 的每专家全局 atomic + grid barrier + 计数器复位。
- 结果：大 batch e2e −0.8…−3.2%；小 batch 反而慢 0.3–6.7%。
- 原因：约 5 次相互依赖的全局往返，排在量化 WG 的 HBM 流量后面，每次往返都被拉长。

**v2a（`tp_prep_v2a.py`）**
- 结构：每个排序 WG 自己读全部 id 做直方图，不用全局 atomic。
- 结果：反而比 v1 慢（T=1024 24.8 vs 18.4 us）。
- 诊断：给 kernel 加了编译期开关 SKIP，可以跳过 hist / scatter / pad / sort / quant 中的某几部分（见 `prof.py`），定位到四个问题：
  - padding 用 64 步展开的 readlane 循环，还带运行时取模，只在少数 wave 上跑，受单 wave 的指令发射限制（5–11 us）；
  - 直方图要多次依赖往返，自己区间的 id 和权重在直方图之后才读，又多一次往返；
  - 越界路由全部计到同一个 dummy 槽，LDS atomic 串行 64 路；
  - **bug**：量化时 wave 的最后一个奇数行被处理两次。结果不变，但 T ≤ 4864 时 x8 和 out 清零的写都翻倍；v1 同样有这个问题。

**v2b（新的 `tp_prep.py`）**
- 修改：
  - 自己区间的 id 和权重在直方图之前发出；
  - 直方图用 16 B 读，一次往返完成；
  - 每个 lane 有自己的 dummy 槽；
  - padding 由全部排序 wave 按专家分摊；
  - 量化改为按行对处理，奇数尾行单独处理；
  - 至少 16 个排序 WG。
- 单 kernel 冷 L2（us）：

  | T | aiter（排序 + 量化） | v1 | v2a | v2b |
  |---|---|---|---|---|
  | 1 | 12.6 | 14.2 | 13.0 | 3.8 |
  | 16 | 17.1 | 17.8 | 18.4 | 4.9 |
  | 1024 | 17.9 | 17.1 | 21.2 | 11.9 |
  | 2048 | 29.5 | 20.7 | 28.7 | 15.1 |
  | 4096 | 39.6 | 38.2 | 40.6 | 23.1 |
  | 8192 | 59.5 | 47.1 | 49.8 | 40.4 |
  | 32768 | 228.2 | 186.7 | 188.8 | 184.3 |

- 剩余瓶颈：T ≤ 2048 时排序部分在关键路径上，T=1024 时 9.3 us，而只做量化是 7.6 us。
- 一个误判：SKIP 分解显示 hist 和 scatter 单独去掉各省 1.4 / 0.2 us，一起去掉却省 5.7 us。先怀疑 barrier 强制等待了预发的 load，查 ISA 后排除（barrier 前只有 `lgkmcnt(0)`）。真正的原因是分解本身不可加：
  - 去掉 hist 后所有偏移都是 0，scatter 的分散写落在同几个 cache line 上，代价被掩盖；
  - 去掉 scatter 后，自己区间的 load 被死代码消除。
- 真实瓶颈是 scatter：每个 CU 约 64 条完全分散的 4 B 写指令，16 个 WG 时约 4 us。

**v2c（v2b + 每个 WG 的路由数按规模自适应）**
- 规则：rng = clamp(next_pow2(M·topk / 64), 256, 2048)，即约 64 个排序 WG。
- 取舍：WG 多了 scatter 分散到更多 CU；但每个 WG 都要重复读全部 id，WG 太多在大 T 时 L2 流量过大（T=32768 时 rng 256 要 242 us）。

  | T | v2b（rng 2048） | rng 256 | rng 512 | rng 1024 | rng 4096 | 只做量化（下界） |
  |---|---|---|---|---|---|---|
  | 1024 | 11.9 | **7.6** | 8.2 | 9.7 | — | 7.6 |
  | 2048 | 15.2 | **11.4** | **11.3** | 12.6 | — | 10.3 |
  | 4096 | 23.0 | 20.9 | **20.3** | 20.6 | — | 19.6 |
  | 8192 | 40.4 | 41.8 | 38.9 | **39.0** | 43.9 | 36.1 |
  | 16384 | 87.8 | 98.7 | 92.5 | 89.2 | 86.9 | — |
  | 32768 | **184.1** | 241.6 | 203.0 | 194.0 | 183.8 | 177.9 |

- 表中 rng 4096 一列以及 rng 2048 的复测来自第二次运行（16384 时 rng 2048 复测为 90.4）；大 T 时两次运行间相差约 ±3 us，2048 和 4096 在噪声内持平。
- T ≤ 4096 已接近只做量化的下界；更大的 T 时，整个 kernel 基本就是读 x、写 x8、清零 out 的 HBM 流量，T=32768 时约 670 MB。

### 3.4 megamoe 的 producers / lag 扫描（`20261114_mega_sweep/`）

- `sweep.py`：每个设置起一个新的 8 卡 job，先对 fp32 参考检查一次（全部 cos ≤ 8.2e-6），再按 `test_a8w4_megamoe_ep8.py` 的方式计时（每次迭代 flush、host + device barrier，取最慢 rank 的中位数），只跑 megamoe。
  - `producers`：发送 route 的 producer WG 数（8 的倍数）；
  - `lag`：每个队列里 gemm2 落后 gemm1 的组数（每组 2 个 block），实际领先量为 min(组数, lag)。
- e2e（us，20 次迭代；括号内是相对默认 16 / 2 的差）：

  | 8 / 4 | 398.7（+2.2%） | 576.0（+0.2%） | 939.9（+0.7%） | 1693.7（+1.4%） | 3138.0（+3.0%） |

  | 32 / 1 | 391.9（+0.5%） | 605.2（+5.3%） | 958.9（+2.7%） | 1690.8（+1.3%） | 3169.0（+4.0%） |

- **producers 16 最好**：同一 lag 下的 30 组比较中，8 和 32 全都更慢。8 慢 0.3–3.7%（T=2048 时 2.3–2.5%），32 慢 0.2–2.6%（T ≥ 4096 时 0.9–2.6%）。
- **lag 1 明显更差**：
  - T=4096 时慢 3.5–4.1%，8192 时慢 1.2–1.7%，三种 producers 都如此；
  - producers 16、T=4096 时，finish（等待其他 rank）从 54.6 增至 80.6 us，即 rank 间的完成时间更不均衡。
- **lag 4 只在 T=4096 更快**：
  - 扫描中三种 producers 都同向（−1.9% / −1.4% / −1.2%）；
  - 用 ABBA 顺序复测（producers 16，40 次迭代，各两次，数据在 `result.txt` 后半部分）。连同扫描，4096 时 lag 2 三次为 574.1 us（均值），lag 4 三次为 566.6 us，−1.3%；
  - 改善来自 mega（最慢 rank，525.5 → 519.6）和 finish（53.9 → 46.9），均为三次均值。
- **原因**：
  - 4096 时每个 rank 有 40–53 个 block，每个队列 5–7 个，即 3–4 组。lag 4 使领先量等于组数，相当于每个队列先发完全部 gemm1 再发 gemm2；
  - lag 2 时，gemm2 与只领先 2 组的 gemm1 交错，流水线太短（推测 gemm2 任务因此更常等 done 计数）；
  - 均匀路由下 T ≤ 2048 时每个队列只有约 4 个 block（2 组），lag 2 和 lag 4 的调度完全相同，结果也相同；
  - T ≥ 8192 时组数在 5 以上，二者持平（±0.3% 以内）。
- **噪声**：默认 16 / 2 在 T=32768 的四次测量为 3143.6（baseline，测试脚本中与 MORI 路径交替运行）、3046.8、3079.7、3075.7，相差约 3%，所以 32768 处小于 3% 的差不作结论。
- **结论**：
  - 不需要按 T 选参数；
  - 默认 lag 2 改为 4 没有变差的点，4096 处 −1.3%。但本次只测了均匀路由；偏斜路由下各队列组数差别大，需要验证后再改默认值，因此本次没有改。

## 4. 反思

- **一开始没抓住重点范围**：先在 ≤16 tokens 上做了 split-K，后来才转到 program.md 强调的 1024–32768。以后先按重点范围做基线和分解，再决定方向。
- **HBM 负载下的依赖往返很贵**：v1 有 5 次全局往返，每次都被量化的 HBM 流量拉长。融合 kernel 中，与流式访存并行的那个角色必须避免依赖链。
- **单 wave 的长串行循环受指令发射限制**：每条 VALU 约 4 个周期，64 步展开、带取模的循环要花好几 us；要把工作摊到所有 wave 上。
- **跳过部分代码的分解不能简单相加**：去掉 hist 让 scatter 的分散写变成集中写，去掉 scatter 让 load 被死代码消除。这导致把 scatter 的代价算到了直方图头上。分解结果要用改参数（rng）的实验交叉验证。
- **FlyDSL 的 JIT 缓存 key 不包含 callable 闭包**：编译期开关要用 int，否则会拿到缓存里的旧 kernel。dump ISA 要加 `FLYDSL_DUMP_IR=1` 来绕过磁盘缓存。
- **噪声**：T=8192 时内容相同的输入放在不同 buffer，GEMM 也会差 2.5%；大 batch 下 <1% 的 e2e 差不能当结论。要同进程交错多轮，并用 kernel 级数据交叉验证。
- **扫参数要结合调度代码**：ep_mega 的领先量是 min(组数, lag)。扫描之后读了代码才明白，lag 2 和 4 只在每个队列 3–4 组（T≈4096）时不同；先读代码就可以只测有差异的点。不同设置分在不同 job 里，无法交错计时，所以对唯一的差异点做了 ABBA 复测。
- **对比实验发现了旧 bug**：v1 / v2a 的奇数尾行被量化两次（结果不变、流量翻倍）。拆分计时和逐位比对都应作为常规手段。

## 5. 后续方向（按 1024–32768 的预期收益排序）

1. **GEMM 本身**：T ≥ 2048 时融合 kernel 占 e2e 的 90% 以上（8192：802 / 846 us）；T=1024 时 gemm1 读 W 只有约 2.4 TB/s，约为 HBM 带宽的一半。
   - 重写 gemm2：更大的 M tile，解码后的 W 经 LDS 共享（README 11 节）；
   - 提高 gemm1 的 MFMA 利用率。
2. **去掉 atomic 的归约**：参考 ROCm/aiter#7706 等，route 行以 fp8 写出再 `moe_reduce`，流量比 bf16 少一半，需要在 gfx942 上重测。如果成功，tp_prep 的 out 清零（T=32768 时 268 MB 写）也可以省掉。
3. **EP 整层的通信**：
   - 用 mori 的按 token 桶调度（ROCm/mori#1001）和 combine_in_view；
   - rank 去重（aiter / DeepEP），xGMI 流量约 −34%。
4. **mega**：
   - 借鉴 DeepGEMM Mega MoE，把 count 与 arrival 打包进一个 atomic，并改用自复位 barrier，减少生产者/消费者握手的往返；
   - 默认 lag 改为 4（3.4：T=4096 −1.3%，其余持平），先用偏斜路由验证；producers 16 已是最优，不需要按 T 选参数。
5. **TP 小 batch**：把 split-K gemm1 并入 `kernels/ep_gemm.py`，加一个 TP 类别（tp prep + split-K EP gemm1 + tp_gemm2），T ≤ 8 时 −23…−56%。
6. **重调 TP 调优表**：tp_prep 降低了 prep 的成本，并减少了小 batch 的 block 数，bm32 / bm64 和 tp2k / tp1k 的交界可能移动。

## 6. kernel 替换建议与本次落地

| 场景 | 建议 | 状态 |
|---|---|---|
