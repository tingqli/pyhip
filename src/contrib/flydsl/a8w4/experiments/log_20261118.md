# 实验日志 2026-11-18：EP 整层的小 batch 单 kernel（megamoe small）

环境：8×MI300X（gfx942，304 CU，750 W），FlyDSL 0.3.2，torch 2.9.1+rocm7.2，MORI（uncached
symmetric heap，默认 4 GB）。形状：MiMo-V2.6-Flash EP8，H 4096、I 2048、256 个专家（每卡 32）、
topk 8，token 均分到 8 个 rank。计时一律用 kernelkit（L2 flush + 8 份权重副本轮换，各 rank 对齐
后取最慢的 rank，ABBA 交错，`<base>#2` 为噪声带）。实验目录：`20261118_mega_small/`。

## 1. 来源与动机

- **来源**：ROCm/aiter `aiter/ops/flydsl/kernels/mega_moe/mega_moe_small_m.py`（MegaMoEV2 的
  small-input 路径，gfx950，DeepSeek-V4 EP8 形状）：quant、dispatch、GEMM1、GEMM2、combine 融合成
  一个 kernel；dispatch 直接把每一路写进目的卡上该专家的固定槽位（目的卡 `running[expert]` 上的
  系统级 atomic 给出行号），没有计数交换和排序；目的卡等所有源卡的完成 flag 后建 tile 表；GEMM2
  把加权后的行直接写回源卡的 combine 输入，最后由每个 rank 自己把 topk 行求和。
- **动机**：原表在 ≤256 tokens 选 `mori`（169–189 us），`mega` 慢 4–7%；`mega` 在 64 tokens 的
  分解（`test_a8w4_megamoe_ep8.py -t 64`）：quant 6.5、prep（计数交换）18.4、plan 8.0、mega 162、
  finish 32 us，5 次 launch 加两次跨卡同步。64 tokens 时每卡约 28 个活跃专家，W 读取下限约
  84 us（12 MB/专家，4 TB/s），整层有 85 us 以上的空间。

## 2. 实现（gfx942 上的改编）

`kernels/ep_mega_small.py`（`megamoe.MegaMoeSmallEpA8W4`，`moe_ep` solver `mega_small`），设计见
kernel 文件的模块文档。与 aiter 的不同之处：

| 部分 | aiter（gfx950） | 本包（gfx942） |
|---|---|---|
| GEMM | MXFP8 A × MXFP4 W | `_kloop._make_core` 的 a8w4 tile：fd2 W 流进 VGPR，fp8 A 每 (行, 128) 一个 f32 scale（gemm1 用 ep_mega 的 TR epilogue） |
| 量化 | 每路（token, slot）一个 wave，MXFP8 | 每个 token 一个 wave，量化一次，发往 topk 个目的卡；同一 token 的 8 个槽位 atomic 由 lane 0–7 一次发出 |
| 源卡完成信号 | 最后一个 producer 写 flag（epoch，parity 双缓冲） | 每个 producer 在自己的 store 完成后往各目的卡的 `done[me]` 上加 64/P；目的卡等 epoch·64（与 P 无关，各 rank 的 P 可以不同） |
| 建 tile 表 | owner CTA 建表、发布 plan 字 | 每个 WG 自己读 32 个计数、在 wave 0 里做前缀和（同样的结果），不发布、少一跳 |
| 工作分配 | 每 XCD 一个计数器，切片无窃取 | 每 XCD 一段 gemm1 + 一段 gemm2 unit（同一批 m-tile，gemm2 多半读本 XCD 写的 a2）；本段取完后去其他 XCD 的计数器取剩余（先普通 load 探测） |
| combine | 最后 `reducers` 个 CTA | WG b 负责 token b, b + GRID, …（b < 本卡 token 数）；最后一个 WG（两级计数）复位计数器后发 flag |
| epoch | 入口 ticket 计数器的代数 | `ctl[SC_EPOCH]`，最后一个 WG 写回 |

固定槽位容量 = tmax（所有 rank 合计的 token 上限，默认 1024）：symmetric buffer 约 196 MB
（rx 128 MB + combine 输入 64 MB），本地 a2 约 20 MB。

## 3. 实验

### 3.1 正确性（`check_small.py`，`pytest a8w4/tests/test_a8w4_megamoe_ep8.py -k small`，`kernelkit check --graph`）

- 均匀 / 热点路由，1–128 tokens/rank，idle rank、单 token、`[0,1,37,300,5,128,99,0]`、约 1/16
  槽位为 -1：cos 差 0.7–3.8e-4（与 `mega` 同量级），无 NaN；silu / situv2，bm 16 / 32 / 64。
- CUDA graph：kernelkit check（capture + 回放 vs eager：逐位相同；重复调用逐位相同，bm32 与 bm64
  逐位相同）；pytest 的回放序列（两个 graph 交替、中间夹 eager，padding 行为 -1）全部通过。

### 3.2 第一个版本（`ab1.md`）

| tokens | mega_small bm32 | mori s16 | mega p32 l2 |
|---:|---:|---:|---:|
| 64 | 155.2 | +15.2% | +23.1% |
| 256 | 162.0 | +15.7% | +23.7% |
| 512 | 179.2 | +37.0% | +16.3% |
| 1024 | 266.5 | +35.2% | −9.7% |

### 3.3 时间线（`timeline_instrumentation.diff`：编译期开关 TL，每个 WG 在阶段末和每个 unit 前后写 `s_memrealtime`；`timeline.py`）

- 64 tokens，rank 0：producer 的槽位 atomic 2.5 us 返回，store 完成 11 us，plan 13 us；
  gemm1 unit 约 46 us（512 KB W）、gemm2 unit 约 24 us（256 KB），每个 unit 进 K 循环前约
  4–6 us，unit 之间 1.5 us，每 WG 3 个 unit；最后一个 WG 133 us，combine 完 141 us。
- K 循环本身：512 KB / 40 us × 304 CU ≈ 3.9 TB/s，已在带宽上限；损失在每个 unit 的填充、
  尾部和 dispatch。

### 3.4 改动与 A/B（`ab2.md`–`ab5.md`）

| 改动 | 结果 | 结论 |
|---|---|---|
| token 先在 producer 之间分散（`t = bid + P·wave`，原来 `8·bid + wave`） | 64 tokens 的 dispatch 11 → 8 us | 落地：一个 CU 发出全部远端 store 太慢 |
| x 行的 load 放在槽位 atomic 之前 | 在上面一项之内 | 落地 |
| 每个 producer 直接加 `done`（取代本地计数 + 最后一个 producer 写 flag） | 少一次本地 atomic 往返 | 落地 |
| 跨 XCD 窃取剩余 unit | 尾部更短（时间线） | 落地 |
| gemm2 的路由权重、源 id 在等 m-tile 之前就发出，peer 基址放 LDS；ratio 表的 load 提前（`pre_a` / `post_a`） | unit 开头的 4–6 us 不变 | 落地（去掉了 epilogue 里的依赖链），但证明那段是 W 预取的填充（README 10 节第 27 条） |
| WPC 2（每 CU 2 个 WG）、ARB 128、NO 128 | ±2%（bm32 + wpc2 有 spill） | 不用 |
| W 走 cache（bcm 0/0） | +7…+9%（≤512）；1024 −3.8% 但 bm64 更好 | 不用 |
| bm 16 / 32 / 64 | ≤256 相同；512 起 bm16 慢 25–33%；1024 bm64 −12%（专家行数 32 左右，bm32 要读两遍 W） | knob bm ∈ {32, 64} |
| producers 8 / 16 / 32 | 8：1024 +2.4%；32：±0.6% | 固定 16 |
| 远端 store 的 cache 位 0 vs sc0\|sc1\|nt | 相同（`timeline_scm0.txt`） | 保留 sc0\|sc1\|nt |
| tmax 2048（`ab4.md`） | 2048 tokens 时 bm64 与 mega 持平（364.6 vs 365.6 us） | tmax 留在 1024（symmetric buffer 少一半） |

## 5. 反思

- 先用时间线把一次调用拆开（dispatch / plan / 每个 unit / combine）再改，比盲扫 knob 有效：
  dispatch 的 11 us 一眼就能看出是 producer 分配的问题；unit 开头的 5 us 用两个改动排除掉
  「依赖链」的解释后，确定是 W 预取的填充。
- 时间线开关会让 kernel 多一种编译变体：按 README 9.5 节的约定没有留在 kernel 里，存成了
  diff。

## 6. 后续方向（按收益）

1. 跨 unit 的 W 预取：一个 unit 的最后 2·PF 个 K tile 时发出下一个 unit 的前 PF 个 W tile，
   GEMM 阶段有望再快 10%（每 WG 3 个 unit × 约 5 us）。
2. 2048 tokens：bm64 已与 mega 持平；加上 1 之后可能反超，那时把 tmax 提到 2048（约 384 MB）。
3. dispatch 与上一层计算重叠（另一个 stream 先发 producer），或按 DP 不均衡调 producer 数。
4. sglang 接入：`mega_small` 是第三套协议，与 `mega`、`mori` 都不能混用（`moe_ep_sglang.md`）。
