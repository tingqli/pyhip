# 实验日志 2026-11-15：a8w4 MoE 的 TP / EP / mega，重点 1024–32768 tokens

环境：8×MI300X（gfx942），FlyDSL 0.3.2，torch 2.9.1+rocm7.2。形状：MiMo-V2.6-Flash，H 4096，topk 8；
TP8 = I 256、256 个专家；TP4 = I 512；EP8 = I 2048、每卡 32 / 256 个专家。
计时一律冷 L2、取中位数，候选在同一进程内交错多轮。§3.3 发现旧协议（每次都用同一份权重）有偏差，之后的计时每次调用换一份权重副本（8 份，`ref.WCOPIES`）。
上一份日志：`log_20261114b.md`（tp_prep、split-K gemm1、mega producers / lag 扫描）。

## 3. 实验

### 3.1 EP gemm 的调度旋钮：prio / pf / st / acm（`20261115_ep_prio/sweep.py`，`{l128,m64}_{main,ext}.txt`，`m64_pf1.txt`）

- **做法**：在 l128（2048–32768）和 m64（1024–2048）上交错计时各变体，5 轮，确认时 7 轮。这些旋钮不改 W 的 cache 策略，不受 §3.3 的计时偏差影响。
- **prio**（MFMA 前后 `s_setprio`，让同一 SIMD 上的 2 个 wave 轮流发 MFMA）：
  - l128 两个 gemm 都开：+0.8…+2.7%；
  - 只开 gemm2：32768 时 −1.2%，在噪声内；
  - m64：+0.5–0.7%。
  - 结论：没有收益。2 wave / SIMD 的结构里加优先级换不来 HipKittens 式的 ping-pong。
- **pf 1 / 4**（W 的 K-tile 预取深度，默认 2）：
  - l128 持平；
  - **m64 gemm2 pf 1：−1.5 / −1.8 / −1.6%（1024 / 1536 / 2048，7 轮）**。另放一个与它完全相同的配置作为噪声基准，结果一样；
  - 两个 gemm 都 pf 1：约 −1.3%。
- **st 1 / 3**（A 写 LDS 的步长）：持平。8192 时 −1…−2%，但噪声大。
- **acm 0**（A 走 cache）：−0.4…−1.6%，幅度小；没在轮换协议下复测，未落地。

### 3.2 W 的 cache 策略 bcm：同一份 W 计时下的"收益"（`20261115_ep_prio/*_bcm*.txt`，`20261115_mega_bcm/result*.txt`）

`bcm` 是 W 读的 cache modifier：2 = nt（全部配置的默认），0 / 1 = 走 cache（二者等价）。旧协议每次计时调用前 flush（读 512 MB），用的是同一份 W：

| 配置 | 改动 | 结果 |
|---|---|---|
| t16 | 两个 gemm bcm 0 + gemm2 pf 1（t16c） | 8 / 16 tokens −9.9 / −9.0% |
| s16 | gemm2 bcm 0 + pf 1 | 64 / 256 / 448 tokens −4.4 / −5.6 / −4.3% |
| s32 | gemm2 bcm 0 + pf 1 | 512 / 768 / 1024 tokens −4.8 / −5.3 / −5.9% |
| m64 | gemm2 bcm 0 + pf 1 | 1024–3072 tokens −6.4…−8.5% |
| l128 | gemm2 bcm 0 | 2048 / 4096 / 8192 / 16384 / 32768：−2.3 / −2.6 / −1.1 / −1.2 / −1.1% |
| l128 | 两个 gemm 都 bcm 0（l128c） | 同上：+3.2 / −0.2 / −0.6 / −2.5 / −2.7% |

- **mega**：给 `compile_ep_mega` 加了 `BCM1` / `BCM2`（gemm1 / gemm2 的 W cache 策略，原来写死 2）。
  - 8 卡、40 次迭代、ABBA 顺序；另跑一个与 bcm22 相同的配置作噪声基准（±0.5%）；
  - bcm01 对 bcm22：2048 / 2560 / 3072 tokens +2.1 / +2.3 / +2.3%，4096 / 8192 / 16384 / 32768 −1.2 / −1.4 / −1.8 / −1.9%；
  - 只改 gemm2（bcm21）持平（−0.9…+1.1%）。
- **a16w4**（共用 CFGS）也"变快"：t16c −11.7%，s16 −6.8%，m64 −3.8%，l128 −1.5%，l128c −2.0%（`a16w4_ab.txt`）。
- 当时把这些改动都落进了 CFGS，并重调了 EP8 表（`20261115_retune/`，各点 winner 普遍"快" 3–11%）。§3.3 证明其中大部分是计时假象，已全部撤回；`20261115_retune/` 只作为反例保留。

### 3.3 计时假象：MALL 留住了被反复读的同一份 W（`20261115_ep_prio/`：`counters.py`、`rotate.py`、`flushcheck.py`、`coldrot.py`）

**疑点**：
- cache 策略只有在数据被重读时才有用。t16 在 8–16 tokens 时每个专家只有一个 block，W 只读一次，却快了 10%；
- a16w4 也同样"受益"。

**TCC 计数器**（rocprofv3；`counters/summary.txt` 是 `counters.py --parse` 的输出，约 59 MB 的原始 CSV 未保留，可用 `counters.py` 头部的命令重新生成）：
- cached 与 nt 的 L2 命中率、L2 miss 数、L2 → 内存（EA）的读请求数都一样，只有 `TCC_STREAMING_REQ` 不同；
- 例（cached / nt）：16384 tokens l128，gemm1 L2 命中 63.1 / 62.2%，gemm2 54.6 / 54.6%；1024 tokens m64 gemm1 EA 读 2.33M / 2.30M；
- 所以差别在 L2 之后，即 256 MB 的 MALL（Infinity Cache）。

**轮换权重**（`rotate.py`）：8 份 W 副本（每份 410 MB）轮流用，不 flush。
- 收益消失或反过来：t16c +5.0…+10.2%，s16 +2.9…+5.0%，s32 +3.6%，m64 +0.9 / −1.3%；
- 只有大 batch 还在：16384 时 l128 gemm2 bcm 0 −2.7%，l128c −4.1%；
- nt 的配置在两种协议下一致。

**flush 方式对比**（`flushcheck.py`；与 nt 的原配置比较。"g2c" 是 gemm2 bcm 0 + pf 1）：

| 协议 | 16 tokens t16c | 256 tokens s16 g2c | 1024 tokens m64 g2c |
|---|---|---|---|
| cold：flush 读 512 MB，同一份 W（旧协议） | −11.3% | −5.9% | −6.5% |
| bigread：flush 读 2 GB，同一份 W | −11.5% | −6.2% | −6.7% |
| **coldrot：flush + 8 份 W 轮换** | **+7.1%** | **+4.1%** | **−0.8%** |
| wflush：flush 先写再读 | +48.5% | +21.1% | +9.4% |
| rotate：只轮换、不 flush | +1.8% | −5.9% | −2.1% |

- 读 2 GB 也冲不掉 MALL 里每次都被读的那份 W，推测 MALL 不让一次性的流式读替换掉它；
- nt 读的 W 显然没留在 MALL 中，所以 nt 配置不受影响；
- 写的 flush 偏差方向相反：cached 配置慢 9–48%；
- 只轮换不 flush 时，结果取决于上一次调用留下的 MALL 状态，也不可靠；
- 真实模型一次前向要读约 19 GB 的 MoE 权重，同一层的 W 不可能在两次调用之间留在 MALL 里。所以合理的协议是 flush 加多份副本轮换（coldrot）。

**副本数**（`coldrot.py --copies`，相对 nt 原配置）：

| 副本数 | t16c @16 | s16 g2c @256 | m64 g2c @1024 |
|---|---|---|---|
| 1 | −11.3% | −5.4% | −6.7% |
| 2 | −2.3% | +4.7% | −0.2% |
| 8 | +10.3% | +4.8% | +0.4% |
| 16 | +5.8% | +3.3% | −1.4% |

- 1 份时偏差最大。2 份时 s16 / m64 已与 8 份一致，t16c 仍偏向 cache（−2.3%，8 份时 +10.3%）。8 份与 16 份方向一致，定为 8 份（`ref.WCOPIES`，每个进程 3.3 GB）。
- m64 gemm2 pf 1（nt）与副本数无关：−1.8…−1.9%。

**定论**（coldrot，8 份副本，5 轮 × 16 次，相对 nt 原配置；`coldrot/*.txt`）：

| 配置 | tokens | 变化 |
|---|---|---|
| t16c | 8 / 16 | +5.5 / +10.3% |
| s16 g2c | 64 / 256 | +2.5 / +4.8% |
| s32 g2c | 512 / 768 | +4.0 / +3.6% |
| **m64 gemm2 pf 1（nt）** | 1024 / 1536 / 2048 | **−1.9 / −1.5 / −1.9%** |
| m64 g2c | 1024 / 1536 / 2048 | +0.4 / +0.5 / −1.3% |
| l128 gemm2 bcm 0 / **l128c** | 4096 | +1.2 / +1.7% |
| 同上 | 8192 | −0.3 / −0.1% |
| 同上 | 12288 | −0.2 / **−1.7%** |
| 同上 | 16384 | −1.5 / **−3.2%** |
| 同上 | 32768 | −2.0 / **−4.2%**（2452.8 vs 2559.8 us） |

- 真实的收益只有一种来源：同一专家的多个 m-block 重读它的 W。
  - EP8 每个专家平均 T·8/256 = T/32 行，6144 tokens 时是 192 行，即 1.5 个 128 行 block；
  - l128c 从这里起才不亏，12288 起明显赢；
  - 更小的 batch 里 W 只读一次，走 cache 反而慢 2–10%。
- a16w4 在轮换后（`a16w4_final.txt`）：m64 pf 1 为 0.0 / −0.4%（1024 / 2048）；l128c +0.2%（4096）、−2.2%（16384）。没有回退。

### 3.4 只保留真实收益，在轮换协议下重调全表（`20261115_retune2/`）

**改动**：
- CFGS 撤回到 HEAD，只保留 m64 gemm2 `pf=1` 和新配置 `l128c`；
- `tune.py` 的 tune / verify 每次计时调用换下一份 W 副本（`--wcopies`，默认 8）。

**全表重调**：`run.sh` 用 8 卡（每个形状 4 个进程），约 2 分钟。共 2070 行，没有 BAD / FAIL。

**与 HEAD 表比较**（`compare.py` → `compare_vs_head.txt`）：
- 新表在新协议下测得；"old-cfg-now" 是 HEAD 选中的配置在新表中的时间；
- 175 个点里 54 个 winner 变了：

| 形状 / 范围 | 变化 | 新 winner 比 HEAD 的选择 |
|---|---|---|
| EP8 6144–32768 | l128 → l128c | silu −0.8 / −2.7 / −2.6 / −1.9 / −2.3 / −3.7%，situv2 −1.6 / −0.8 / −2.1 / −1.8 / −2.2 / −2.8%（6144 / 8192 / 12288 / 16384 / 24576 / 32768） |
| EP8 1536（silu）、2048（situv2） | l128 → m64（pf 1） | −2.1%、−0.8% |
| TP8 1024 / 1280 | tp2k bm64 → tp1k bcm2 ks1 | −0.4 / −0.6% |
| TP4 6144 | tp1k bcm1 ks1 → ks2 | −2.2% |
| TP8 12–96（situv2 12–128）、TP4 6–16 | `g1bcm1` → `g1bcm2`（gemm1 的 W 改回 nt） | −4.7…−7.7% |
| EP8 8–320 | t16 / s16 互换 | −0.1…−1.3%，噪声级 |

- **TP 小 batch**：HEAD 表（11-12 生成）在 12–96 tokens 选的 `g1bcm1` 也是这个假象的产物。
  - 验证（`tp8_wcopies/`）：同一份脚本只改副本数；
  - 16 tokens 时，1 份副本 `tp2k bm32 g1bcm1 g2nt4` 最快（56.5 us），8 份副本 `g1bcm2` 最快（62.7 us）。
- TP ≥2048 仍然选 tp1k bcm1（W 走 cache），这些点在新协议下也是 bcm1 最快。
- **situv2 与 silu**（`situv2_stats.py`）：
  - 同一配置的 situv2 / silu 中位数比是 1.016（TP8、EP8 都是；p5–p95 为 1.001–1.037 / 1.001–1.032）；
  - winner 不同的点：TP8 11 个、EP8 4 个，差 0.1–0.8%。
- **AUTO**（`ep_gemm.AUTO`，表外的默认）加上 `(5120,"l128"),(None,"l128c")`。
  - 448 tokens 时 AUTO 选 s16，比 s32 慢 9.9%。这是原有的 480 阈值，没有改（§5）。

**8 进程并发对计时的影响**（`concurrent/run.sh`）：
- 做法：GPU0 跑 `tune verify`（EP8 2048–32768），先单独跑，再在 GPU1–7 各跑一个 EP8 tuner 时跑，重复两次；
- 表中配置的 loaded / alone 比：1.004 / 0.995 / 0.984 / 1.005 / 1.008 和 0.999 / 1.006 / 1.007 / 1.016 / 1.005（均值 1.003）；
- 两次单独运行之间也差 −1.5…+0.5%。所以并发没有系统性影响，8 卡并行调优有效。

**路由抽样**：
- verify 在 4096 tokens 测得 474 us，表中是 441.5 us。原因是 EP8 每个专家平均 128 行，正好是 BLOCK_M：
  - tuner 的三次抽样（种子 101·T + r）需要 44 / 45 / 44 个 l128 block；
  - verify 的抽样（种子 7 + T）要 48 个（+9%），总行数也多 2–3%。
- 2048 tokens 时 l128 总是 32 个 block，m64 则在 44–51 个之间。所以 m64 与 l128 谁快取决于抽样：
  - 表中 l128 快 2.9%；
  - verify 的抽样下 m64 快 2%。
- 表中相差 <3% 的配置在一次抽样下可能互换，这是负载本身的离散性，不是计时误差。

### 3.5 megamoe 的 W cache 策略：轮换复测（`20261115_mega_bcm/rotate.txt`、`rotate2.txt`）

- **做法**：`sweep.py --wcopies 8`，每个 rank 8 份 W 副本，每次计时前设 `mega.W`；40 次迭代，ABBA 顺序；bcm22 的副本作为噪声基准（±0.2%）。
- **结果**（相对 bcm22）：

  | T（总） | bcm01 | bcm00 | bcm20 |
  |---|---|---|---|
  | 2048 | +1.5% | +1.3% | — |
  | 3072 | +1.0% | +1.1% | +0.3% |
  | 4096 | −2.4 / −2.6% | −2.5 / −2.2% | −0.8% |
  | 8192 | −1.7% | −1.8% | — |
  | 16384 | −2.3% | −2.2% | — |
  | 24576 | −3.6% | −3.7% | −2.5% |
  | 32768 | −2.0 / −1.6% | −3.1 / −2.0% | +0.5% |

- **结论**：
  - 收益主要来自 gemm1 的 W；bcm00 ≈ bcm01，保留 bcm01；
  - 与单卡 EP 不同，mega 从总 4096 tokens 起就受益。这时每卡 512 tokens，每个本地专家平均约 128 行，即一个 block；而 ep3k 要到每专家约 1.5 个 block 才不亏；
  - 推测 mega 的持久调度让同一专家的 block 在时间上更靠近，W 更可能还在 cache 里，但没有验证（§5）。
- **落地**：`megamoe.py` 编译两个 launch：`launch`（bcm22）和 `launch_big`（bcm01）。本卡 tokens ≥ `big_tokens` = BLOCK_M·E_LOCAL / topk = 512（总 4096）时用后者。

### 3.6 mega 的通信暴露（`20261115_mega_overlap/overlap.py`、`result.txt`）

- **做法**：沿用 luwei 的方法，把 peer 表（`recv_a`、`recv_scale`、`down_ids`、`recv_w` 和 / 或 `out`）换成本卡的 scratch，使 dispatch 和 / 或 combine 只写本地，`ws` 仍是远程。每次迭代先跑一次正常调用，让接收 buffer 里是正确的行。producers 16，lag 2，30 次迭代。
- **结果**（相对 p2p 的 e2e 差，us）：

  | T | p2p e2e | dispatch 本地 | combine 本地 | 都本地 |
  |---|---|---|---|---|
  | 2048 | 389.3 | −9.8 | −6.5 | −17.6（4.5%） |
  | 4096 | 574.4 | −15.5 | −7.4 | −21.7（3.8%） |
  | 8192 | 937.0 | −29.5 | −21.3 | −51.0（5.4%） |
  | 32768 | 3030.3 | −51.9 | +14.7（finish 跳到 145 us，不作结论） | −116.6（3.8%） |

- **结论**：
  - 通信只暴露 4–5%。FP8 combine 或 dispatch 去重最多回收 1–2%，与 luwei 的 FP8 combine（2449 → 2434 us）一致。
  - 全本地时，mega 阶段在 32768 是 2828 us。单卡 EP8 做同样多的本地工作，gemm1 + gemm2 是 2401 us（§2，W 走 nt，与这里的 bcm22 相同）。8 进程并发不影响单卡计时（§3.4），所以约 15% 的 mega 时间是结构性开销：
    - 16 个 CU 做 producer；
    - 持久任务的等待和 lag；
    - kernel 内的拷贝。
  - 这些不是通信造成的。

| 2048 | 390.0 | 436.5 | 1.12× | 400.2 | 436.0 | 1.09× |
| 4096 | 568.0 | 727.1 | 1.28× | 580.6 | 728.6 | 1.25× |
| 8192 | 923.8 | 1098.6 | 1.19× | 944.1 | 1098.3 | 1.16× |

## 4. 反思

- **最大的收获是找到计时协议的漏洞**：
  - flush 只清掉了 L2，W 还留在 MALL 里。每次都计时同一份 W，会让 W 走 cache 的配置系统性地快 5–13%；
  - 我先把这些"收益"当了真：改了 CFGS、重调了 EP8 表，直到发现 t16 的收益解释不通（每个专家只有一个 block，没有重读）才回头查；
  - 以后要做到：
    1. 收益要有机制解释，解释不通先怀疑测量；
    2. 用计数器定位到具体层级：L2 指标完全一样，说明差别在 L2 之后；
    3. 计时协议要贴近部署：真实模型各层 W 不同，W 不会留在 MALL 里，所以要轮换副本。
  - HEAD 表的 TP 小 batch 选择（`g1bcm1`）也是这个假象造成的，新表快 5–8%。log a / b 的 EP 配置扫描都用 nt W，结论不受影响。
- **先确认协议再调参**：这次在有偏的协议下做了一整轮 EP8 重调（`20261115_retune/`），全部作废。对任何改变数据复用的旋钮（W / A 的 cache 策略、光栅化顺序），都应先在多个协议下各测一个点。
- **EP8 的工作量本身是随机的**：
  - 4096 tokens 时每个专家平均正好 128 行，l128 的 block 数随抽样变化 ±9%，verify 与表差 7%；
  - 比较配置必须在同一组抽样上交错计时（tuner 就是这样做的），跨 run 比较要把抽样差异算进去。
- **先量上限再投入**：mega 的通信只暴露 4–5%，比直觉小得多。FP8 combine 一类的通信优化预期有限，结构性开销（约 15%）才是大头。
- **小插曲**：
  - 脚本命名为 `profile.py` 会遮蔽标准库，torch import 失败；
  - `breakdown.py --local L` 是每个 token 的本地专家数，不是 rank 号；第一次并发实验因此每张卡的负载都不同，已删除，§3.4 重做；
  - 改 kernel 源文件（哪怕只改注释）会改变 FlyDSL 的缓存 key，第一次调用要重新编译。
- **旋钮扫描的边际收益已经很低**：prio / pf / st 中只有 m64 gemm2 pf 1 有 1.5–1.9%。GEMM 的进一步收益要靠结构性改动（§5）。

## 5. 后续方向（按 1024–32768 的预期收益排序）

1. **W 在 cache 中的复用**：l128c 在 32768 时 −4.2%，说明重读 W 有价值；mega 在每专家一个 block 时就能受益。
   - 让同一专家的 m-block 在时间和 XCD 上靠近，参考 ROCm/aiter#7965 的 L2 + MALL 光栅化；ep_prep 已按 XCD 分桶，可以从这里改；
   - 弄清 mega 为什么在 4096 就受益。需要能反映 MALL 命中的手段，TCC 计数器看不到。
2. **GEMM 结构**（T ≥ 2048 时仍占 90% 以上的时间；整层只到 fp8 峰值的 52%（EP8）/ 44%（TP8））：
   - BM 256 或 8-wave ping-pong（HipKittens），摊薄 fp4 解码和 LDS 上 A 的读；
   - 重写 gemm2（README §11）；
   - STRIP16 权重 + scale 同址存放（ROCm/aiter#7966、vllm-project/vllm#67642）。
3. **mega 的结构性开销（约 15%）**：
   - producer 占用的 16 个 CU、任务等待 / lag、kernel 内拷贝；
   - 通信相关的改动（FP8 combine、dispatch 去重）最多 1–2%；
   - log b 的 lag 4 仍待在偏斜路由下验证。
4. **MORI 路径**：试 ROCm/mori#999 的 MI300X EP8 调度表（8192 / 16384 −2.1…−4.4%）；扫 block_num / warp_num_per_block。
5. **小修**：
   - AUTO 在 448 tokens 选 s16 比 s32 慢 9.9%，可把阈值 480 调到 448 以下；
   - acm 0 在轮换协议下复测。
6. **测量规范**：tune、verify 和三个 8 卡 bench 已默认轮换 8 份副本。以后凡是涉及 cache 策略的实验都要在轮换协议下做；EP8 的比较用固定的几组抽样。
