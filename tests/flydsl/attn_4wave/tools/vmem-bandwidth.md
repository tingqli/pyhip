## 结论

- **没有漏测。** load和store均覆盖`lane_bytes = [16, 8, 4]`、5种连续线程数和8种cache位，
  各120项，共240项；下方汇总表逐项列出全部组合。
- **共同最优：64线程连续。** load用16 B/lane达到4273 GB/s；store用4或8 B/lane约3560 GB/s。
- **访问宽度：** load应选16 B/lane；store的4与8 B基本并列，16 B约低5%。
- **稀疏布局代价高：** `4线程 x 4 B`仅为load 412-2278 GB/s、store 194-730 GB/s。
- **cache位没有稳定赢家：** 最佳布局候选的21次复测差异小于0.3%；`sc1`只在低聚合布局上明显退化。

## 搜索空间

[vmem-bandwidth.py](vmem-bandwidth.py)固定每个workgroup为256线程（4 wave），搜索：

- 操作：`load`、`store`。
- 连续线程数：256、64、16、8、4。
- 每lane字节数：16、8、4，对应`dwordx4`、`dwordx2`、`dword`。
- cache位：`sc0`、`nt`、`sc1`的全部8种组合。

默认共$2 \times 5 \times 3 \times 8 = 240$个case，执行顺序按固定seed随机化。

## 控制变量

地址映射为：

```text
group = thread_id // contiguous_threads
lane  = thread_id % contiguous_threads
```

每个线程组扫描独立且等长的stripe。所有配置每次launch覆盖相同有效字节数，地址不重叠，
只改变单条wave指令内的地址聚合形态。

- 每个kernel使用64 KiB LDS，固定每CU一个4-wave workgroup。
- host验证80个唯一CU，并验证每个workgroup的wave 0-3分别落到4个SIMD。
- 每个pipeline槽使用独立vector地址寄存器；每32条VMEM执行一次`vmcnt(0)`。
- load使用32组独立目标，store复用一组源寄存器；不同布局可能有不同VGPR数，但均由
  64 KiB LDS固定为相同的一WG/CU、每SIMD一wave拓扑，且不允许scratch。
- 16 B load的编译器资源报告可为3 waves/SIMD，但实际launch每CU只有一个4-wave WG；
  host验证四个wave分别位于四个SIMD，因此各SIMD实际仍只有一个目标wave。
- ISA检查目标VMEM数量、指令宽度、cache位和无scratch；host检查load sink与store首尾写回。
- 默认每workgroup扫描8 MiB，8个buffer轮换；每case额外预热后，用`cudaPerf`采9次并取中位数。

cache策略名称只表示原始ISA位组合，不预设其cache层级语义。

## 使用

只检查矩阵和显存需求，不访问GPU：

```bash
/usr/bin/python3 tests/flydsl/attn_4wave/tools/vmem-bandwidth.py \
  --grid-blocks 80 --dry-run
```

完整测试命令：

```bash
HIP_VISIBLE_DEVICES=4 /usr/bin/python3 \
  tests/flydsl/attn_4wave/tools/vmem-bandwidth.py \
  --device 0 --grid-blocks 80 \
  --json /tmp/vmem-bandwidth.json --csv /tmp/vmem-bandwidth.csv
```

工具打印load/store各自的Top配置；JSON保留随机执行顺序、每次时延和完整矩阵元数据。
